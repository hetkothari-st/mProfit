# Robustness audit — 2026-10-19

Scope: dependency failure, jobs & crons, process & deploy, input & data integrity.
Base: `origin/main` @ `14b1a76e`. Static read, sequential, no fixes applied.

Why the P0s matter: `index.ts:329` exits the process on any unhandled rejection
(correct — state is untrusted after one), and `railway-api.toml` sets
`restartPolicyType = ON_FAILURE`, `restartPolicyMaxRetries = 5`. So any
fire-and-forget promise without a `.catch` is a whole-API restart, and a
repeating one can exhaust the retry budget and leave the service down.

## P0 — process killers / silent job loss

| ID | Finding | Evidence | Fix |
|---|---|---|---|
| R-01 | `runMfPeerRankJob` has `try/finally`, no `catch`; cron calls it as `void runMfPeerRankJob()`. Any DB/query error at 00:30 IST → unhandled rejection → API exits. Every other cron entry was checked and does catch. | `jobs/mfPeerRankJob.ts:213-225`, `:243` | Add `catch` → log + return zero result (match siblings). |
| R-02 | PF scraper `emit()` calls `void transition(...)`, which is a bare `prisma.pfFetchSession.update`. Session row gone (cancel, account delete) → P2025, or DB blip → unhandled rejection → API exits, mid-scrape, for every user. Fires many times per scrape. | `jobs/pfFetchWorker.ts:197`, `services/pfFetchSessions.service.ts:25` | `.catch(log)` at the call site. |
| R-03 | PF fetch worker, PF nudges, Split share-link reconcile, Split digests and **Succession (legacy transfer)** crons are registered only at the *end* of `runStartupSync`. (a) Unguarded DB calls before that (`stockMaster.count`, `ageOfLatest`) throw on a boot-time DB blip → caught upstream as "Startup sync failed" → those 5 jobs never start for the life of the process, no further signal. (b) `ENABLE_STARTUP_SYNC=false` disables them entirely. (c) Otherwise they start minutes late (after AMFI/Yahoo/commodity sync). Succession is a dead-man switch — silent non-run = missed delivery. | `jobs/startupSync.ts:70`, `:81-87`, `:107-112`; `index.ts:302` | Move the 5 starters into `index.ts` listen callback beside the other `start*` calls. |

## P3 / verify

- R-16 No distributed lock on crons. Fine at 1 replica; a deploy-overlap window or a 2nd replica double-runs Succession, digest and reminder emails. Postgres advisory lock per cron if replicas ever >1.
- R-17 Node `keepAliveTimeout` default 5 s behind Railway's proxy — classic cause of sporadic 502s. Verify against Railway edge idle timeout before changing.
- R-18 `startMfNavHistoryBackfillJob` and `startMfFactsheetJob` exist but are never called. Comment says "let the boot sequence wire it" — confirm intended or forgotten.
- R-19 `routes/mcp.routes.ts:55-56` `void transport.close()` / `void server.close()` without catch — low odds, same crash class as R-02.

## Checked and OK

- Async route handlers: 63/67 route files use `asyncHandler`; the 2 bare async handlers (`aiAssistant /chat`, `mcp POST`) have their own try/catch.
- Every other cron entry (26 checked) catches; `priceJobs` all go through `runGuarded`.
- Other fire-and-forget helpers (`writeAuditLog`, rental/insurance auto-match hooks, notify*) catch internally.
- Redis: rate limiter has a fallback; oauthState uses `enableOfflineQueue: false`; import / gmail-scan / doc-sort enqueue via `enqueueBounded`.
- Prisma outer/inner transaction timeouts aligned (15 s / 30 s).
- Pagination limits capped by zod everywhere checked; upload size limits on all multer instances.
- Unhandled rejection / exception logged before exit.
