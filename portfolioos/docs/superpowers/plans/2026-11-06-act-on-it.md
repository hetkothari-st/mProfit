# Act on it + Track record Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the advisor engine's recommendations into "Act on it": timed, backed suggestions with a lifecycle (accepted → confirmed in data → measured against doing nothing), a track record, a pop-up and alerts capped at 2 a week, and automatic pausing of suggestion types that miss their own promises.

**Architecture:** Extend, don't fork, the existing advisor engine (`services/advisor`). `AdvisorRecommendation` stays the single store and gains tracking columns; rules gain a `promise` and a `measurement` block; new rules are added for the new suggestion types. A new `services/actOnIt/` module owns the lifecycle (actions, confirmation matching, outcome measurement, rule health, prompts) and one nightly job drives it. The web app gets an `/act-on-it` page (mockup v4), a global pop-up, and the Advisor page loses its recommendation list.

**Tech Stack:** Express + Prisma 5.22 + Postgres RLS, decimal.js, zod 4, node-cron; React 18 + TanStack Query + Tailwind; Vitest.

**Spec:** `docs/superpowers/specs/2026-11-06-act-on-it-design.md`

## Global Constraints

- Money is Decimal (decimal.js); API money as strings; no `parseFloat`/`Number()` on money.
- Every figure and rationale is code-generated and deterministic; LLM prose only via the existing `proseConsistency` guard.
- Rules are pure: no I/O, no `Date.now()` (read `facts.asOf`).
- New user-scoped tables: RLS policy `app_is_system() OR "userId" = app_current_user_id()`, FORCE RLS, GRANT DO block, and registration in `USER_SCOPED_MODELS` (`src/lib/prisma.ts`).
- Prompts: at most 2 (pop-ups + alerts combined) per user per rolling 7 days; urgent bypasses (hard deadline within 7 days with money at stake).
- The ₹ total counts only CONFIRMED (by data) and SKIPPED outcomes that were MEASURED; "I did this elsewhere", accepted-unseen, not-measured and before-tracking rows are listed but excluded.
- Named funds stay behind the existing signed-methodology gate; otherwise category-level.
- Bank-spending-derived facts only for users with spending consent (`hasSpendingConsent`).
- Compliance line: "SEBI-registered investment adviser, INA [placeholder]. Advice, not a guarantee of returns." INA from AppSetting `advice.ria_registration` (string), placeholder text when unset.
- UI: mockup v4 — dark theme, lime accent, Fraunces headings, all numbers `.numeric-display` (Inter Tight tabular); projection lines straight.
- Public repo: no real user figures in tests/fixtures/docs.

## Review Focus

- Engine re-run while a recommendation is ACCEPTED (not yet confirmed): must not supersede or re-open it; confirmation still matches. Test in Task 3.
- A rule stops emitting (cash got spent) while the recommendation is OPEN: becomes WITHDRAWN, never counted as skipped. Test in Task 3.
- Prices/NAVs missing for the measurement window: outcome stays PENDING (never 0, never a guess). Test in Task 6.
- Two prompts already sent this week and a non-urgent new suggestion arrives: no pop-up/alert, but it shows in the section. Test in Task 8.
- A paused rule type: its open suggestions withdrawn, no new ones shown, history kept. Test in Task 7.

### Task 5: New rules (one file each, pure, unit-tested)

**Files:** create in `services/advisor/rules/`: `idleCashParking.rule.ts`, `regularToDirect.rule.ts`, `ltcgBooking.rule.ts`, `stoppedSip.rule.ts`, `fdMaturity.rule.ts`, `loanRefinance.rule.ts`, `advanceTax.rule.ts`, `emergencyFund.rule.ts`, `healthCover.rule.ts`, `fundUnderperforming.rule.ts`; register in `rules/index.ts`; constants in `constants.ts`. Tests: `src/services/advisor/rules/<name>.rule.test.ts`.

Values (spec §7, assistant's documented calls):
- idleCashParking: fires when spendingConsent, monthlySpending known, savingsRatePct known, and balance > 3× monthlySpending in ≥ 6 of last 12 months including the last 3; amount = latest balance − 3× spending, rounded down to ₹10,000, min ₹50,000; expected liquid yield `LIQUID_FUND_YIELD_PCT = 6.5` (constant, documented); gain = amount × (6.5 − savingsRate)%; only if gain ≥ ₹2,000; riskBand LOW; liquidity "1 working day"; measurement NAV_VS_CASH 365d, baseline {amountInr, savingsRatePct, referenceSchemeCode (largest-AUM direct growth liquid fund in MfSchemeMeta/MfSchemeAum)}; expires 30d.
- regularToDirect: per regular holding with a direct sibling and both TERs; gain/yr = value × (regularTer − directTer)%; only if ≥ ₹500/yr; note exit load and capital gains in rationale; riskBand LOW; DIRECT_VS_REGULAR 365d, baseline {regular, direct scheme codes, value}; expires 60d.
- ltcgBooking: only 1 Feb–31 Mar; headroom = exemption − fyRealised; book min(headroom, unrealisedEligible) if ≥ ₹10,000; tax saved = amount × ltcgEquityPct; urgentUntil 31 Mar when ≤ 7 days left; TAX_SAVED to 31 Mar; expires 31 Mar.
- stoppedSip: a SIP with a missed month in a month where NIFTY fell ≥ 5% from its 3-month high; MEDIUM risk; SIP_UNITS 365d, baseline {schemeCode, monthlyAmount, months}; expires 45d.
- fdMaturity: maturity within 14 days; compare FD rate with liquid yield and best FD rate if known; urgentUntil maturity when ≤ 7 days; RATE_DIFF 365d; expires on maturity.
- loanRefinance: market rate ≤ user rate − 0.5pp and outstanding ≥ ₹5 lakh and monthsLeft ≥ 24; gain = interest saved over 12 months minus 1% processing fee estimate (stated); RATE_DIFF 365d; expires 60d.
- advanceTax: next due within 15 days and amount due > 0; urgentUntil when ≤ 7 days; TAX_SAVED (234C interest avoided, 1%/month × 3); expires due date.
- emergencyFund: liquid assets < 3× monthly spending (known); NOT_MEASURED; expires 30d.
- healthCover: HEALTH sum insured < ₹10 lakh (`HEALTH_COVER_FLOOR_INR`, documented) or none while user has dependants/family members; NOT_MEASURED; expires 90d.
- fundUnderperforming: a weakFunds entry with an alternative (from the MF analytics alternatives, behind the named-fund gate; else category wording); MEDIUM risk; FUND_VS_ALT 365d, baseline {held, alt scheme codes, value}; expires 60d. regularToDirect and fundUnderperforming never on the same holding (underperforming wins: switching to the alternative's direct plan covers both).
- Conflict reconciliation in the engine: if IDLE_CASH_PARKING and CASH_DEPLOYMENT both target the same surplus, keep CASH_DEPLOYMENT only when a risk profile exists, else keep parking; LTCG_BOOKING and TAX_HARVEST never on the same holding (harvest wins).

### Task 6: Confirmation matching + outcome measurement

**Files:**
- Create: `services/actOnIt/confirm.ts`, `services/actOnIt/measure.ts`, `services/actOnIt/measureMath.ts` (pure)
- Test: `src/services/actOnIt/measureMath.test.ts`, `test/services/actOnIt/confirmMeasure.test.ts`

Interfaces:
- `confirmFromData(userId, now): Promise<number>` — for ACCEPTED, OPEN, SNOOZED, DISMISSED, EXPIRED recs with a matcher: NAV_VS_CASH → a BUY transaction in a liquid/overnight fund within ±20% of amount after createdAt (≤ 45 days); DIRECT_VS_REGULAR → regular holding gone/reduced and direct sibling bought; SIP_UNITS → SIP instalment in the following month; TAX_SAVED (ltcg) → realised LTCG increased by ≥ 80% of suggested before 31 Mar; RATE_DIFF → FD closed/renewed or loan lender/rate changed; FUND_VS_ALT → held fund reduced and alternative bought. Sets `confirmedAt`, `confirmedBy='DATA'`, `confirmation`, status DONE.
- `measureDue(userId, now): Promise<number>` — for recs past `createdAt + horizonDays` (or interim "so far" stored in `outcomeDetail.soFar`): CONFIRMED by data → outcome = acted − baseline; SKIPPED (DISMISSED/EXPIRED, not confirmed) → outcome = −(what acting would have gained), labelled missed; NOT_MEASURED method → `NOT_MEASURED`; missing NAV/rate data → stays PENDING.
- Pure math in `measureMath.ts`: `navGrowth(amount, navStart, navEnd)`, `cashGrowth(amount, ratePct, days)`, `terDrag(value, terPct, days)`, `sipUnits(...)`.

- [ ] Steps: pure math tests (₹1,80,000 at 3% for 365d = ₹5,400; NAV 100→106.5 = ₹11,700; difference ₹6,300); DB tests: a confirmed liquid purchase measured; a skipped one measured as missed; missing NAV → PENDING; implement; PASS; commit.
